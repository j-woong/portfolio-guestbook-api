# 05. 함께 걷기 (멀티플레이)

| 키워드 | 한 줄 설명 |
|---|---|
| WebSocket | 한 번 연결하면 서버와 브라우저가 계속 메시지를 주고받는 통신 방식 |
| TextWebSocketHandler | 연결됨·메시지 받음·연결 끊김을 각각 메서드로 처리하는 스프링 클래스 |
| Relay(중계) | 서버가 받은 메시지를 다른 접속자들에게 그대로 전달하는 것 |
| ConcurrentWebSocketSessionDecorator | 여러 스레드가 한 연결에 동시에 보내도 안전하게 해 주는 래퍼 |
| Origin 검사 | 허용한 사이트에서 온 연결만 받는 것 |

## 공통 개념: 서버는 중계만 한다

방명록 API는 "요청 → 응답"으로 끝나지만, 다른 사람의 위치는 서버가 먼저 알려줘야 한다. 그래서 `/ws/park` 주소에 WebSocket을 열었다. 서버는 게임 규칙을 판정하지 않는다. 각 브라우저가 자기 위치를 보내면, 값이 정상인지만 확인하고 나머지 사람들에게 전달한다. DB에도 저장하지 않는다.

## 주고받는 메시지

| 방향 | 메시지 | 언제 |
|---|---|---|
| 서버 → 나 | `{"t":"hello","id":"내 번호","players":[...]}` | 접속 직후 한 번. 지금 공원에 있는 사람들 |
| 나 → 서버 | `{"x":1.2,"z":-3,"f":0.5,"y":0,"n":"닉네임"}` | 움직였을 때 0.1초마다, 가만히 있으면 2초마다 |
| 서버 → 다른 사람 | `{"t":"s","id":"번호","x":...,"n":"닉네임"}` | 누군가의 상태가 올 때마다 |
| 서버 → 다른 사람 | `{"t":"bye","id":"번호"}` | 누군가 나갔을 때 |

## 접속 `afterConnectionEstablished`

- 이미 30명이면 종료 코드 4001로 닫는다. 프론트는 이 코드를 보고 "공원이 가득 찼어요"를 띄운다.
- 방문자 번호는 서버가 UUID 앞 8자리로 정한다. 클라이언트가 번호를 정하게 두면 남의 번호를 흉내 낼 수 있다.
- 세션을 `ConcurrentWebSocketSessionDecorator`로 감싼다. 한 사람에게 보내는 메시지는 다른 사람들의 스레드에서 동시에 올 수 있는데, WebSocket 세션은 동시에 보내면 예외가 난다. 방명록의 `compute`, EFY의 비관적 락과 같은 "동시에 들어오면?" 문제다.

## 상태 받기 `handleTextMessage`

클라이언트가 보낸 값은 믿지 않는다.

- 메시지 크기는 512바이트로 제한한다.
- 한 사람이 0.04초 안에 또 보내면 버린다. 초당 25개가 한도다.
- `x`, `z`, `f`, `y`가 숫자가 아니면 무시한다. 숫자면 지도 범위 안으로 잘라 낸다.
- 닉네임은 제어 문자를 지우고 12자로 자른다. 비어 있으면 "손님"이다.

## 나가기 `afterConnectionClosed`

목록에서 지우고 나머지 사람들에게 `bye`를 보낸다. 브라우저를 그냥 닫아도 호출된다. 네트워크가 끊겨 호출이 늦어지는 경우를 대비해, 프론트는 10초 동안 소식이 없는 사람을 화면에서 지운다.

## 연결 허용 `ParkSocketConfig`

`setAllowedOrigins`에 방명록 API와 같은 주소 목록(`app.allowed-origins`)을 넣었다. 다른 사이트에서 이 서버로 WebSocket을 열면 403으로 거절된다.

## 한계

- 접속자 목록이 서버 메모리에 있어서 서버가 한 대일 때만 동작한다. 여러 대로 늘리면 Redis Pub/Sub 같은 것으로 서버끼리 메시지를 나눠야 한다.
- 위치를 클라이언트가 정하므로 순간이동 같은 조작은 막지 못한다. 포트폴리오 산책용이라 판정 서버는 두지 않았다.
- 한 사람의 메시지를 나머지 전원에게 보내므로 인원이 n명이면 메시지는 n²으로 늘어난다. 그래서 30명으로 제한했다.
